# Phase 5 — Harden adopt mode

**Goal:** close the five project shapes `install.sh --adopt` has never been pointed at, so that
everything built on top of it reads a repo description that is actually true.

**Why now:** every downstream command reads `.kmpilot.json` and trusts it — `appModule` decides
where integration points 2/3/4 are written, `packagePrefix` decides every generated package
statement, `managedFeatures` decides which code is graded strictly. Phase 6 adds a command that
*rewrites existing source* against those values, **across a whole project in one run**. A wrong
`appModule` today produces a misplaced Koin line a human notices; the same wrong value under
Phase 6 misplaces every feature it touches and every package it rewrites. Detection accuracy stops
being a convenience and becomes a safety property.

Phase 2 found 13 defects. Three came from reading the code; **ten came from pointing adopt at a
shape it had never seen**, and none from re-running the happy path.
[`ADOPT-TEST-BACKLOG.md`](ADOPT-TEST-BACKLOG.md) is the list of shapes still unseen — this phase
is that file, executed.

**Branch:** `phase-5-adopt-hardening`

> **Before you start:** read [`README.md`](README.md) → *Branch and PR conventions* and
> *`update.sh` delivery tiers*.
>
> **Prerequisites:** none beyond Phase 2. Every fixture in this phase is generated by
> `scripts/adopt-matrix.sh`; the real repos (`bookshelf`, `bookshelf-featuredir`, `Kickoff26`)
> already exist and are only used as confirmation.

## In scope

Backlog items 2–6, in the backlog's own priority order. Item 1 (a repo that already has a
`feature/` directory) closed 2026-08-04 via `managedFeatures`.

### 1. Two plausible app modules — ambiguity is never detected

`detect_app_module` (install.sh:524) returns the **first** module matching each signal and labels
it `strong`. The `weak` path already prompts on a TTY (install.sh:720) with a candidate list —
that machinery exists and works. What is missing is that **two** modules both calling `startKoin`
never reach it: the first match returns `strong` and the second is never seen.

**Fix:** collect *all* matches per signal tier instead of returning on the first. More than one
match in the winning tier ⇒ `APP_MODULE_CONFIDENCE=ambiguous`, which takes the same prompt path as
`weak`, worded for ambiguity rather than absence. Non-TTY ⇒ refuse and print the candidates, since
a coin flip here is silent and expensive.

### 2. No code at the app module's root package

`detect_pkg_prefix` (install.sh:559) computes the longest package prefix shared by the app
module's sources. With every file in a sub-package (`…app.ui`, `…app.di`, `…app.nav`, nothing in
`…app`) the prefix still resolves, but nothing confirms it — and this is the exact code path that
once produced `com.example.bookshelf.` with a newline glued on.

**Fix:** assert the result is a well-formed package (no trailing dot, no whitespace, ≥2 segments),
cross-check it against the Android `namespace` / `applicationId` when one exists, and confirm on
TTY when the two disagree.

### 3. A package prefix unrelated to `rootProject.name`

`rootProject.name = "Bookshelf"` with `com.acme.internal.reader` sources. The generated-resources
package derives from the root name, the Kotlin package from sources — independent values, and the
scoped rename touches both. Currently untested together.

**Fix:** no code change expected; a matrix variant that asserts the vendored core lands as
`bookshelf.core.designsystem.generated.resources` *and* `com.acme.internal.reader.designsystem`,
then builds.

### 4. A monorepo where the KMP app is not at the repo root

`--adopt` runs in the current directory and assumes it is the Gradle root. `android/`, `ios/`,
`backend/` with the KMP project one level down is ordinary in company codebases.

**Fix:** when `settings.gradle.kts` is absent, search one level down before refusing, and name the
directory to run in. A refusal that says *"run this from `./android`"* is a pass; a refusal that
says *"not a KMP project"* about a repo that plainly contains one is the failure being tested for.

### 5. A project already using `kmpilotLibs` or `core/kmpilot*`

Someone who hand-vendored KMPilot before adopt mode existed. Re-adoption must recognise that state
rather than duplicating a catalog or colliding on module names. The `already-adopted` variant
covers a repo with `.kmpilot.json`; this is the same shape **without** the manifest.

**Fix:** detect KMPilot artefacts independently of the manifest (catalog name, `core/*` package
contents), and report the pre-existing state before writing anything.

## Out of scope

- **Groovy DSL** — parked with an explicit unpark trigger (one real adopter refused). The
  `groovy-dsl` variant already asserts the refusal stays clean; nothing changes here.
- **The capability-map model** and **Maven Central publishing** — both parked, both unchanged.
- **Any migration or translation work** — that is Phase 6, and this phase is its prerequisite.
- **Rewriting a target's architecture.** Adopt adds a pipeline; it does not refactor their code.

## Steps

1. Item 1 (ambiguous app module) first — it is the only one with a real silent-wrong-answer
   failure mode, and the prompt machinery already exists.
2. Item 2, then 3 — both touch `detect_pkg_prefix`'s output contract.
3. Item 4 (monorepo) — pure refusal-quality work, no writes involved.
4. Item 5 (pre-vendored) — needs a fixture mutation before the detection is written.
5. For **every** variant: break the fix, watch the variant go red, restore it. A variant that
   cannot fail is worse than no variant.
6. Confirm against the real repos (`bookshelf`, `bookshelf-featuredir`, `Kickoff26`) — adoption
   output must be byte-identical to before the phase except where a bug was fixed.

## Exit criteria

- [x] Two modules both bootstrapping Koin ⇒ prompts on TTY, refuses with both candidates named
      when non-interactive. Never picks silently.
- [x] App module with no root-package sources ⇒ `packagePrefix` is exactly the shared prefix,
      well-formed, and cross-checked against the Android namespace.
- [x] `rootProject.name` unrelated to the package prefix ⇒ resources package and Kotlin package
      land independently, and the target builds.
- [x] Run from a monorepo root ⇒ refuses naming the directory to run in, not "not a KMP project".
- [x] A hand-vendored KMPilot with no `.kmpilot.json` ⇒ recognised and reported, never duplicated.
- [x] `scripts/adopt-matrix.sh` at **25 variants**, all green, each proven able to fail.
- [x] Re-adopting the three real repos produces no diff versus pre-phase output beyond fixes.
- [x] `ADOPTING.md`'s published compatibility table matches the variant list exactly.

## Risks

- **Prompting more often makes adopt feel less automatic.** Mitigation: only ambiguity prompts,
  and only when a wrong answer would be silent. A confident detection must stay silent.
- **Five fixes, one PR.** Each is small and independently revertable, but the diff to `install.sh`
  is broad. Keep one commit per backlog item so a bisect stays useful.

---

## Downstream delivery

`install.sh` is a release asset — fixes reach users the moment a release ships. `ADOPTING.md` is
stripped on install and lives upstream only. Nothing here changes `.kmpilot.json`'s schema, so the
release back-compat contract is untouched.
