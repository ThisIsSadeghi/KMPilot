# Phase 6 step 9 — hand-built test-bed projects

Test beds for the **whole** pipeline: `install.sh --adopt` **and** `/kmp-to-kmpilot`. Every project
here is created **unadopted** on purpose — adoption is part of what is under test, so a project that
arrives already adopted skips the first half of the run.

Written 2026-08-06, before any of them exist. Ideas only; the user builds them and adds their own.

**Where:** `~/KMPProjects/kmpilot-testbeds/{NN}-{name}` — a new folder, so nothing here collides with
`bookshelf`, `bookshelf-featuredir`, `Kickoff26` or `nonconforming-target`, which must stay
byte-identical after read-only runs.

**Scope: KMP only.** Pure-Android input is Stage C's job and is parked at the end of this file.

> **This file is a specification, not a work order.** The **user** creates these projects himself —
> one folder each, one separate Claude session each, by pasting that project's prompt block. A
> KMPilot session reading this file must **not** start generating repos from it: the isolation is
> the point (each block is written for a cold context with no KMPilot in it), and a test bed
> generated by the same session that later migrates it proves much less. **The migration test
> begins only once the projects exist and the user says to start.** Until then, step 9 has nothing
> to run — say so rather than manufacturing a test bed.

## How to use this file

Per project, two steps:

1. **Generate an empty KMP project** (the JetBrains wizard, `kmp.jetbrains.com`) into
   `~/KMPProjects/kmpilot-testbeds/{NN}-{name}`. Android + iOS + desktop unless the project says
   otherwise. Do not adopt it. Do not add KMPilot to it.
2. **Open a fresh Claude Code session in that directory** and paste that project's block. One block,
   whole thing, nothing else — no preamble to add, no two pieces to stitch.

**Each block is fully self-contained.** Every one repeats the same framing — *this is a deliberately
non-conforming test bed, the anti-patterns are the deliverable, leave them in* — because each lands
in its own repo, its own folder and its own cold context, with no KMPilot skills, no `patterns.md`
and no memory of this file. The repetition across blocks is deliberate; do not factor it out.

Prose **outside** the blocks is for KMPilot's side of the work (why the shape matters, what to watch
for) and is not meant to be pasted.

## Rules of engagement

For the KMPilot side, not the building session. These make a finding attributable — skipping them
turns a real bug into an argument about whether the project was broken to begin with.

1. **Each project must build and run before KMPilot touches it.** APK installed, screens reachable.
   A post-migration failure means nothing if the baseline was never proven. **Exception:** 01, which
   is refused by reading files before anything is compiled — buildability is optional there and its
   prompt says so.
2. **Tag the baseline:** `git tag pre-kmpilot` on a clean tree, after the app is proven to run. That
   is what a post-migration diff and `git switch -` get compared against.
3. **One shape per project.** Two novelties in one repo means a failure cannot be attributed to
   either. The exceptions are marked *(deliberately combined)* and say why.
4. **Never hand-write `.kmpilot.json`.** If a project has one, adopt mode refuses it, correctly.
5. **Two of them must do a real network call and be launched on a device after migration.** Four of
   the nine findings so far survived a green `assembleDebug`, a green strict `archTest` and green
   iOS + desktop compiles. Building is not evidence.
6. **Leave one project dirty at migration time** (not at adopt time — adopt refuses a dirty tree by
   design). Sequence: adopt clean → make uncommitted edits → then migrate, so `begin` has a dirty
   tree to absorb.

**Record per project:** every finding, and *which phase caught it* — adopt / discovery / plan /
clean / integrate / compile / **launch**. The launch column is the one that has been earning its
keep.

## Tier 0 — the adopt gauntlet

Cheap, fast, and none of them reach migration. What is under test is that the **refusal is correct,
readable and actionable**. A wrong refusal is the failure mode this phase says costs a user's trust,
and these are the only projects where a refusal is the pass condition.

The eight gates in `adopt_detect()`, in the order they fire: no `settings.gradle.kts` → Groovy DSL →
not a git repo → dirty tree → `.kmpilot.json` already present → `rootProject.name` will not sanitize
→ no module with `src/commonMain` → `--app-module` with no `src/commonMain`.

### 01 `adopt-groovy` — Groovy DSL, with a competing gate

**The edge worth building in:** a Groovy root that *also* has a KMP build one level down. Two gates
compete — the wrong-level one and the Groovy one — and which fires decides whether the user is told
the truth. Nobody has run that combination.

```
You are working in a freshly generated Kotlin Multiplatform project. Nothing has been built on
top of it yet.

Context, because it changes what "good" means here: this is a deliberately non-conforming
test-bed project. I am testing a migration tool that converts existing KMP projects to a strict
architecture, and I need realistic input for it. Your job is to build this project INTO a
specific awkward shape and to LEAVE it that way. Do not improve the architecture, do not clean
up naming, do not centralize anything, and do not add tests. A tidy version of this project is
a failed test bed.

Hard rules:
- Do NOT create a file named .kmpilot.json, do NOT run any install.sh, and do NOT add a
  dependency on any module named core:common, core:data or core:designsystem.
- Keep it small: one feature, one screen, roughly 5-8 files.
- Current stable versions, minimal dependency set.
- BUILDABILITY IS OPTIONAL for this project, unusually. The Kotlin Multiplatform Gradle plugin
  in the Groovy DSL is awkward; if it will not resolve, stop, leave it as it is, and record
  exactly where it failed in NOTES.md. The tool I am testing refuses this repo by reading files,
  before any build runs, so a non-resolving build still tests what I need.

THE SHAPE TO BUILD — a KMP project on the GROOVY Gradle DSL, with the real app one level down:

- Convert every build script to Groovy: settings.gradle (not settings.gradle.kts), build.gradle
  (not build.gradle.kts). No .kts file may remain anywhere.
- The ROOT settings.gradle includes only `:tools` — a plain kotlin-jvm module with a main().
  There must be no src/commonMain at this level at all.
- The real KMP app lives in mobile/ with its OWN settings.gradle, also Groovy: one composeApp
  module plus one feature module, one screen each.
- Inside the feature, ordinary messy code: androidx.compose.material3.* imported directly,
  hardcoded English strings at their use sites, a ViewModel with MutableStateFlow mutated via
  `_state.value = _state.value.copy(...)`, and a repository class with no interface.

WHEN DONE, in this order:
1. Write NOTES.md at the repo root: what shape this project is, which awkward choices are
   deliberate, and exactly where the Groovy build failed if it did.
2. `git init` if there is no repo yet, commit everything, then `git tag pre-kmpilot`.
3. Report back: the file tree, and a numbered list of the deliberate oddities you left in.
```

**Expected outcome:** refused at the repo root. Which reason it reports matters — "Groovy DSL is not
supported" or "the KMP build is one level down" — because both are true here.

```
  * a screen split in two: a thin composable that takes the ViewModel, and a ViewModel-independent
    one that takes the state plus callbacks.
- NO androidx.compose.material3.* imports in feature code at all. Put a small hand-rolled
  component layer — a button, a text wrapper, a screen container with a top-bar slot, a theme —
  in a shared ui module, and have features use only that.
- Every user-facing string, including every contentDescription, in
  composeResources/values/strings.xml and read via stringResource. No literals anywhere in the UI.
- One Koin module per feature, named feedModule and profileModule, each listed once in the app's
  startKoin. No god module, no service locator.
- Screens take callback parameters (onBackClick, onItemClick) — never a NavController.
- Exactly ONE Scaffold in the whole app, in the app shell. Feature screens use the plain container
  from the ui module, never their own Scaffold.

WHEN DONE, in this order:
1. Write NOTES.md at the repo root: that this project is deliberately CLEAN and is the
   negative-control test bed for "the tool should find nothing to do", plus a checklist of the
   conventions above with the file that demonstrates each.
2. `git init` if there is no repo yet, commit everything, then `git tag pre-kmpilot`.
3. Report back: the file tree, and the checklist with file paths.
```

**Expected outcome:** after adoption the tool reports both features as **already conforming**, does no
rewriting at all, and claims no credit for them in its report.

### `adopt-android-only` — a pure Android app, no `commonMain` anywhere

Every one of those is on the translation table in `PHASE-6-project-migration.md`.

## What to do with the findings

part is not optional — finding 9 was a negative control that had been passing for the wrong reason
since the day it landed, and 61 of the 66 matrix variants still have no registered mutation
