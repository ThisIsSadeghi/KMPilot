# KMP → KMPilot

Bring an **entire existing KMP project** under the pipeline: discover what is there, plan where it goes, clean it into KMPilot shape, wire it up.

**Architecture Reference:** @../_shared/patterns.md

> **Working name.** `/kmp-to-kmpilot` is deliberately literal and deliberately temporary — it says exactly what goes in and what comes out. The published name is settled before the plugin ships.

## What ships today

**Discovery and planning.** The looking half is built and verified; the rewriting half is not.

| Phase | Status |
|---|---|
| **1. Discover** — inventory, dependency order, tier proposals, refusals | ✅ **shipped** |
| **2. Plan** — the written, confirmed migration plan + on-disk resume ledger | ✅ **shipped** |
| 3. Clean — rewrite one feature at a time to zero checker findings | ⬜ not yet |
| 4. Integrate — 4 integration points, specs, `managedFeatures`, report | ⬜ not yet |

**This skill writes exactly one file — `.claude/docs/_project/migration-plan.json` — and no source file, ever.** It ends with a confirmed (or still-draft) plan. If the user asks it to start migrating, say plainly that the rewrite phases land in a later increment — do **not** improvise a migration by hand. Rewriting features without the checkpoint branch and the per-feature checker loop is exactly the unbounded single-pass rewrite the design forbids.

## Scope

**Input:** an **adopted** KMP project (`.kmpilot.json` with `installMode: adopt`) whose features do not follow KMPilot's rules.

Discovery reports which of four situations a repo is in, and only one is a migration target:

| Role | Meaning | Migration target? |
|---|---|---|
| `adopted` | `install.sh --adopt` ran here | **yes** |
| `template` | generated by `install.sh` — features are already KMPilot's | no — findings are `/modify-feature` work |
| `pipeline-source` | KMPilot itself | no — it is the reference implementation |
| `unadopted` | a KMP repo with no KMPilot in it | no — run `install.sh --adopt` first |

An Android-only project is **not** in scope here; that is Stage C (`/android-to-kmpilot`).

## Workflow

```
[USER INVOKES] → Preflight → Discover → Present → Plan → Confirm → STOP (rewrite phases not yet shipped)
```

## Step 1: Preflight

1. Resolve the target repo from `$ARGUMENTS`, else the current working directory. It must contain `settings.gradle.kts`.
2. Verify **Python 3** is available — discovery is a script, not prose:
   ```bash
   python3 --version
   ```
   If it fails, **STOP** and tell the user to install Python 3 (macOS `brew install python3`; Linux via the distro package manager; Windows `winget install Python.Python.3`). Do not work around it.
3. Do **not** pre-read the project's source files to "understand the codebase" first. Discovery does that deterministically in one pass, and a model's separate reading of the same files is what makes a migration and a CI run disagree.

## Step 2: Discover

Run the discovery pass. It reads the whole project and **writes nothing**:

```bash
python3 .claude/skills/_shared/kmpilot_discover.py --root {repo} --report /tmp/kmpilot-discovery.json
```

Rule findings come from `.claude/skills/_shared/kmpilot_check.py`, run in-process at `--baseline` grading — never re-derived by reading the rules yourself. Consume the report.

Full instructions for reading the output: @phases/phase-1-discover.md

## Step 3: Present

Present the inventory to the user in this order — see the phase file for the exact shape:

1. **Role** — and if the repo is not a migration target, say so first and stop there.
2. **Features** — verdict, location, entry point, rule findings per feature.
3. **Shared code** — each package, its proposed `:core:*` tier, the trigger that drove the proposal, and its consumers.
4. **Migration order** — dependencies before consumers; cycles called out as work.
5. **Refusals** — with the reason and the file:line evidence.
6. **Notes** — everything that is not a refusal but changes the plan.

**Tier proposals are proposals.** Discovery decides mechanical facts; where shared code lands is a judgment call the user confirms in the next step. Present each with its evidence and invite correction — never as a settled verdict.

## Step 4: Plan

Turn the inventory into the plan, built from **the report the user was just shown**:

```bash
python3 .claude/skills/_shared/kmpilot_plan.py --root {repo} --discovery /tmp/kmpilot-discovery.json
```

This writes one file — `.claude/docs/_project/migration-plan.json` — and no source. Present the ordered steps, the decisions the plan needs, the refusals and the blocked steps.

Full instructions: @phases/phase-2-plan.md

## Step 5: Confirm

Ask for confirmation with `AskUserQuestion` — confirm as-is · change a tier · take a feature out of scope. Apply corrections and re-present before confirming:

```bash
python3 .claude/skills/_shared/kmpilot_plan.py --root {repo} --set-tier hoist-core-network=data
python3 .claude/skills/_shared/kmpilot_plan.py --root {repo} --mark migrate-legacyweb=skipped
python3 .claude/skills/_shared/kmpilot_plan.py --root {repo} --confirm
```

**Never confirm on the user's behalf**, and never confirm a plan they have not seen in full. The confirmation is the gate the whole phase leans on: it is what makes a large rewrite something the user agreed to in advance.

## Step 6: Stop

State plainly: the plan is on disk, it is confirmed (or still a draft), **no source file was touched**, and the rewrite phases have not shipped yet. Offer the useful next actions that **do** exist:

- `python3 .claude/skills/_shared/kmpilot_plan.py --root {repo} --status` — the plan and its progress
- `python3 .claude/skills/_shared/kmpilot_check.py --all --baseline` — the full rule-by-rule work list
- `/modify-feature` — fix one feature by hand today, with the pipeline's own workflow
- `/review-feature` — review a feature against the rules

Do not offer to start the migration.
