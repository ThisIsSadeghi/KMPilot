# KMP → KMPilot

Bring an **entire existing KMP project** under the pipeline: discover what is there, plan where it goes, clean it into KMPilot shape, wire it up.

**Architecture Reference:** @../_shared/patterns.md

> **Working name.** `/kmp-to-kmpilot` is deliberately literal and deliberately temporary — it says exactly what goes in and what comes out. The published name is settled before the plugin ships.

## What ships today

| Phase | Status |
|---|---|
| **1. Discover** — inventory, dependency order, tier proposals, refusals | ✅ **shipped** |
| **2. Plan** — the written, confirmed migration plan + on-disk resume ledger | ✅ **shipped** |
| **3. Clean** — checkpoint branch, rewrite one step at a time to zero checker findings, restore-and-refuse. Creates the feature modules a monolith never had (`carve`) | ✅ **shipped** |
| **4. Integrate** — `MIGRATION-REPORT.md`, specs, `managedFeatures` promotion | ✅ **shipped** |

**Phases 1 and 2 write no source file at all** — discovery writes nothing, the plan writes exactly one file. Source is only ever touched in phase 3, only from a **confirmed** plan, and only behind a checkpoint branch with a per-step commit. Phase 4 writes no source either: one report and one manifest field.

Never hand-write a `managedFeatures` entry. Promotion re-runs the checker precisely because a `done` step is a claim — promoting a feature the checker has not passed is how a migration starts lying about itself.

## Scope

**Input:** an **adopted** KMP project (`.kmpilot.json` with `installMode: adopt`) whose features do not follow KMPilot's rules.

Discovery reports which of four situations a repo is in, and only one is a migration target:

| Role | Meaning | Migration target? |
|---|---|---|
| `adopted` | `install.sh --adopt` ran here | **yes** |
| `template` | generated by `install.sh` — features are already KMPilot's | no — findings are `/modify-feature` work |
| `pipeline-source` | KMPilot itself | no — it is the reference implementation |
| `unadopted` | a KMP repo with no KMPilot in it | no — run `install.sh --adopt` first |

An Android-only project is **not** in scope here; that is Stage C (`/android-to-kmpilot`).

## Step 1: Preflight

1. Resolve the target repo from `$ARGUMENTS`, else the current working directory. It must contain `settings.gradle.kts`.
2. Verify **Python 3** is available — discovery is a script, not prose:
   ```bash
   python3 --version
   ```
   If it fails, **STOP** and tell the user to install Python 3 (macOS `brew install python3`; Linux via the distro package manager; Windows `winget install Python.Python.3`). Do not work around it.
3. Do **not** pre-read the project's source files to "understand the codebase" first. Discovery does that deterministically in one pass, and a model's separate reading of the same files is what makes a migration and a CI run disagree.

## Step 2: Discover

Run the discovery pass. It reads the whole project and **writes nothing**:

```bash
python3 .claude/skills/_shared/kmpilot_discover.py --root {repo} --report /tmp/kmpilot-discovery.json
```

Rule findings come from `.claude/skills/_shared/kmpilot_check.py`, run in-process at `--baseline` grading — never re-derived by reading the rules yourself. Consume the report.

Full instructions for reading the output: @phases/phase-1-discover.md

## Step 3: Present

Present the inventory to the user in this order — see the phase file for the exact shape:

1. **Role** — and if the repo is not a migration target, say so first and stop there.
2. **Features** — verdict, location, entry point, rule findings per feature.
3. **Shared code** — each package, its proposed `:core:*` tier, the trigger that drove the proposal, and its consumers.
4. **Migration order** — dependencies before consumers; cycles called out as work.
5. **Refusals** — with the reason and the file:line evidence.
6. **Notes** — everything that is not a refusal but changes the plan.

**Tier proposals are proposals.** Discovery decides mechanical facts; where shared code lands is a judgment call the user confirms in the next step. Present each with its evidence and invite correction — never as a settled verdict.

## Step 4: Plan

Turn the inventory into the plan, built from **the report the user was just shown**:

```bash
python3 .claude/skills/_shared/kmpilot_plan.py --root {repo} --discovery /tmp/kmpilot-discovery.json
```

This writes one file — `.claude/docs/_project/migration-plan.json` — and no source. Present the ordered steps, the decisions the plan needs, the refusals and the blocked steps.

Full instructions: @phases/phase-2-plan.md

## Step 5: Confirm

Ask for confirmation with `AskUserQuestion` — confirm as-is · change a tier · take a feature out of scope. Apply corrections and re-present before confirming:

```bash
python3 .claude/skills/_shared/kmpilot_plan.py --root {repo} --set-tier hoist-core-network=data
python3 .claude/skills/_shared/kmpilot_plan.py --root {repo} --mark migrate-legacyweb=skipped
python3 .claude/skills/_shared/kmpilot_plan.py --root {repo} --confirm
```

**Never confirm on the user's behalf**, and never confirm a plan they have not seen in full. The confirmation is the gate the whole phase leans on: it is what makes a large rewrite something the user agreed to in advance.

## Step 6: Clean

Only from a **confirmed** plan. Cut the checkpoint branch, then work the steps one at a time in the planned order:

```bash
python3 .claude/skills/_shared/kmpilot_migrate.py --root {repo} begin
python3 .claude/skills/_shared/kmpilot_migrate.py --root {repo} next
python3 .claude/skills/_shared/kmpilot_migrate.py --root {repo} checkpoint {step}
#   … run the step's rewrite passes, one cluster at a time, delegating each to the
#     agent the plan names: data-layer, ui-layer, integrator …
python3 .claude/skills/_shared/kmpilot_migrate.py --root {repo} complete {step}
```

Feature source is protected by the `protect-feature-files.sh` hook, so before editing anything under `feature/` run `touch /tmp/.claude-kmpilot-skill-active`, and `rm -f /tmp/.claude-kmpilot-skill-active` when the run ends or exits early.

**One step at a time, in the order `next` gives.** Never batch steps, never pick one by eye, and never let this become a single sweeping pass over the repo — that is the failure every earlier phase was built to prevent. When a pass hits a blocker, `refuse {step} --reason "…"`: it restores the subject to its checkpoint and records the refusal in one action. A refusal is a pass; move to the next step.

A **`carve`** step is the one that creates a module rather than rewriting one — a feature that is still a package inside the app module. Route it to `integrator` and write `detail.buildFileSpec` exactly as given; it carries the JVM level, `androidResources` and serialization-plugin settings that three separate runtime crashes were traced to, none of which a build catches.

Full loop, the cluster→agent map and the resume rules: @phases/phase-3-clean.md

## Step 7: Integrate

Once the steps are worked through, close the run. Generate a spec for each migrated feature first, then finish:

```bash
python3 .claude/skills/_shared/kmpilot_report.py --root {repo} plan     # what it will do
#   … /audit-spec for each migrated feature that has none — never write specs yourself …
python3 .claude/skills/_shared/kmpilot_report.py --root {repo} finish   # promote, report, close
```

`finish` re-verifies every finished feature before promoting it to `managedFeatures`, writes `MIGRATION-REPORT.md`, and marks the closing step done. **Never hand-write a `managedFeatures` entry** — a promoted feature is graded strictly from that moment, so promoting one the checker has not passed makes the migration lie about itself.

Full semantics: @phases/phase-4-integrate.md

## Step 8: Stop

State plainly what happened: which steps are done, which were refused and why, which features were promoted, that the work is on the `kmpilot/migrate-*` branch, and that **`git switch -` undoes all of it**. If the tree was dirty at `begin`, repeat the `git restore --source={ref} -- .` line — that work is inside the checkpoint commit, not on the base branch.

Then say what has **not** happened — nothing was compiled and no tests were run or ported:

- `./gradlew assembleDebug` and `./gradlew archTest` — this migration verifies statically and compiles nothing, and every promoted feature is now graded strictly
- `python3 .claude/skills/_shared/kmpilot_migrate.py --root {repo} status` — progress and checkpoints
- `/test-feature` — pre-existing tests are out of scope for migration; `MIGRATION-REPORT.md` names which features need it most
- `/review-feature` — review a migrated feature against the rules
